Unit III: Static Testing

Ano ang Static Testing?

Sinusuri ang work products (manual o gamit ang tools) nang hindi pinapatakbo ang software. Layunin: makita ang defects nang maaga at pataasin ang quality.
  • Manual reviews: peer reviews, walkthroughs, inspections, code reviews.
  • Automated static analysis: tools tulad ng SonarQube.
  • Puwedeng i-apply sa requirements, designs, documentation, at source code. Halos anumang nababasa at naiintindihang work product ay puwedeng i-review (user stories, backlog items, models, contracts, test charters).

Work products at ano ang chine-check

Nagko-complement sila; walang pumapalit sa isa. Iba-iba ang uri ng defects na nahahanap ng bawat technique, kaya combination ang mas maganda.

Benefits

  • Early defect detection
  • Mas magandang understanding at communication ng stakeholders
  • Mas kaunting corrective effort sa huli
  • Human review + automated tools: hindi kayang saluhin ng tools ang bawat context, lalo na sa security defects.

The Review Process

Software review = structured examination ng work product ng isa o higit pang tao para maghanap ng anomalies, mag-evaluate ng quality, umintindi, o mag-agree, nang hindi ini-execute ang software.

Formal review phases (in order)

  • Planning: pumili ng review type at technique.
  • Kick-off: ipamigay ang document at checklist sa reviewers.
  • Preparation (individual): bawat reviewer nagbabasa nang mag-isa.
  • Review meeting: pag-usapan at i-confirm ang findings.
  • Rework: ang author ang nag-aayos.
  • Follow-up: kino-confirm ng moderator na naayos at isinasara ang issue.

Halimbawa sa slides: Student Enrollment System. Na-flag ang "The system shall process enrollment quickly" kasi ambiguous at hindi testable ang "quickly".

Review techniques (paano nagbabasa ang reviewer)

TechniquePaanoBest for
Ad hocWalang structured guidance; nagre-report habang may napapansinMabilis, low-stakes; nakadepende sa skill; puwedeng may duplicate findings

Hindi mutually exclusive ang techniques (hal. tester na gumagamit ng checklist habang nagre-review mula sa perspective ng tester). Pagpili: objective ng review, uri at kritikalidad ng work product, available na oras, expertise ng reviewers. Isang review meeting = isang review type, pero puwedeng magkaiba ang technique ng bawat reviewer.

Inspections

Formal at systematic na peer review para mag-identify ng defects sa work products nang hindi ini-execute ang software. Structured at defect-focused: naghahanda muna ang reviewers, dodokumentuhin ang defects, at vine-verify na naayos.

Bakit valuable ang inspections?

  • Find problems early: bago lumaki ang problema.
  • Reduce rework: hindi kumakalat ang defects sa design, code, at tests.
  • Improve quality and practices: knowledge sharing, nakikita ang recurring defects.

Static Analysis

Static (program) analysis: process para madiskubre ang semantic properties ng system o program nang hindi ito pinapatakbo.
  • Static testing = mas narrow: source code, AST, bytecode, config files (syntax, logic, technical flow).
  • Static analysis = mas broad: requirements at design docs, client/user needs, system infrastructure.
  • Apat na roles (Rival & Yi, 2020): verification of specifications; verification of programs; synthesis of optimized code; refactoring at maintenance.
  • Input: source code, config files, compiled bytecode. Output: vulnerabilities, defects, requirement deviations, documentation non-compliance.

  • False positives o false negatives
  • Mahabang run time kaya minsan nilalaktawan ng devs

Conclusion: Static Techniques

  • Iniiwasan ang pagkawala ng business reputation, operations, pera, at oras.
  • Mas madaling maintenance at long-term time/cost efficiency.
  • Laging kasabay ng regular na documentation at observation.

Modern applications

  • DevSecOps at CI/CD: security at quality checkpoints sa pull-request phase.
  • Safety-critical / cyber-physical: nilalabas ang timing risks at memory corruption bago ang hardware.
  • Cloud at Infrastructure as Code: cloud misconfigurations, sobrang permissive na IAM roles, software bills of materials.
  • AI-assisted development: flawed logic, vulnerabilities, invalid AI-generated APIs; linting sa ML data pipelines.
  • Smart contracts / blockchain: vulnerability scanning at formal verification bago i-commit.

Unit IV: Testing Administration

Test Planning

Proseso ng pagdedesisyon kung ano ang ite-test, paano, at anong resources ang kailangan bago magsimula ang testing.

Purpose: T.E.S.T.E.R.

  • Target key features
  • Ensure complete requirements
  • Structure activities
  • Tap resources efficiently
  • Establish expected results
  • Recognize risks

Mahahalagang parts ng Test Plan (SCORM / "storm")

  • Scope
  • Objectives
  • Criteria
  • Resources
  • Methods

Product Risk Matrix

Ayon sa ISTQB, ang risk ay factor na puwedeng magdulot ng negatibong kahihinatnan sa hinaharap; ang product risk ay risk na nakakaapekto sa quality ng product. Laging limitado ang oras at budget, kaya risk-based testing ang gabay sa pagpili at prioritization ng test activities.
Risk Score = Likelihood × Impact
Likelihood: gaano kalamang magka-defect o pumalya ang feature? Impact (Severity): gaano kalala ang epekto kapag pumalya?
Mas mataas na score = mas mataas na priority, mas maraming test cases, mas maagang execution, mas malalim na coverage.

Paano gamitin sa planning: (1) Identify risk items, (2) Assess likelihood at impact, (3) Map the risk items, (4) Set test priority at depth.

Test deliverables

Before testingDuring testingAfter testing
Test plan document, test case specifications, test design documentsTest scripts at test data, defect/bug reports, test execution logsTest Summary Report, release notes, installation/configuration guides

Final report: Test Summary

  • Scope of testing: ano ang na-test, ano ang hindi, at bakit
  • Results summary: bilang ng Pass, Fail, Blocked; overall coverage
  • Defect summary: bugs by severity; ilan ang fixed vs open
  • Risk coverage: kinukumpirmang natest nang husto ang high-risk items
  • Quality assessment: overall verdict kung ready na sa release
  • Sign-off: pormal na pagsasara ng test phase

Challenges ng traditional test strategies

  • Defensive design
  • Complexity
  • Continued production failures
  • Maintenance hurdles

Customization of the Test Process

Hindi one-size-fits-all ang testing. Exhaustive testing is impossible at testing is context-dependent. Nakadepende sa Who, What, When, Where, Why, How.
  • Who: sino ang kasali sa testing
  • What: level, types ng tests, techniques, scope
  • When: frequency ng test cycles at execution
  • Where: environment
  • Why: dahilan sa technical decisions
  • How: tools, processes, CI/CD pipelines, frameworks, methodologies
Agile e-commerce mobile appCritical medical device software
WhoDevelopers (unit, smoke); QA engineer (exploratory)IEC 62304: independent test team at reviewer
WhatFunctional at regression testingUnit (MC/DC coverage), integration, system, safety tests
WhenTuloy-tuloy: bawat commit at katapusan ng sprintFixed phases; kailangan ng requirements at approval
WhereShared, staged na kamukha ng productionControlled at validated, may calibrated hardware
WhySpeed kaysa exhaustive documentationSafety at regulatory compliance kaysa speed
HowJenkins/GitHub Actions, Selenium/Appium, Jira, sprint test chartersRequirements Traceability Matrix, IEEE 829 template, Polarion/TestRail

Requirements Traceability Matrix (RTM): Req ID at Requirement, Source, Risk, Test Case IDs, Test Type, Status, Defect ID, Verification.

Budgeting

Test budgeting: sistematikong estimation, allocation, at tracking ng financial, technical, at human capital na kailangan para i-verify at i-validate ang software laban sa specifications.
  • Objectives: resource optimization, risk mitigation, tool at infrastructure provisioning
  • Ibu-budget: manpower; tools at licensing; infrastructure at hardware; training at enablement; contingency / rework (backup funds)

Estimation techniques

  1. Work Breakdown Structure (WBS) / Bottom-Up: hinahati sa maliliit na tasks at pinagsasama
  2. Three-Point Estimation (PERT)
  3. Percentage of Total Project Cost (Top-Down)
  4. Cost of Quality (CoQ) Model

Scheduling

Ginagawang day-by-day timeline ang test plan: ano ang tetestingin, sino ang gagawa, anong pagkakasunod, at hanggang kailan. Nakabatay sa test plan at effort estimation (hindi mo maisi-schedule ang hindi mo pa nasusukat).

Inputs: test plan, estimation, resources, dependencies → test schedule → evaluation at monitoring.

Ano ang humuhubog sa schedule

  • Complexity at size ng application
  • Environment at data (test environments, realistic test data)
  • Team size at skill
  • Risk level ng features (payments, login: mas maaga)
  • Phase dependencies: Unit → Integration → System → UAT, bawat isa naghihintay sa nauna
High-risk features ang unang isinasama sa schedule; may oras pa para mahuli ang critical issues.

Techniques ng test managers

  • Gantt charts: timeline, overlaps, dependencies
  • Critical Path Method (CPM): tasks na direktang nagdidikta ng deadline (halimbawa sa slide: System testing, Weeks 5-6; delay dito = delay ang release)
  • Risk-based scheduling: highest-risk features sa unahan

Standards: ISO/IEC/IEEE 29119-2 (scheduling ay bahagi ng test planning, kasama ang scope at resource allocation). ISTQB Test Manager syllabus (scheduling ay core at ongoing na responsibility, kaugnay ng estimation at monitoring).

Common challenges
  • Late requirement changes
  • Resource conflicts sa pagitan ng teams
  • Underestimated retest time
  • Delays mula sa upstream development
Best practices
  • Maglagay ng buffer time
  • I-align sa dev at release schedule
  • Mag-prioritize by risk
  • Regular na mag-review at mag-adjust
Sabay na ninenegosyo ang schedule at budget: ang compressed timeline ay kadalasang mas mataas na gastos o mas kaunting coverage.

Conclusion: Unit IV

  • Planning, customization, budgeting, at scheduling ay magkakaugnay.
  • Risk ang common thread: nagdedesisyon kung ano ang unang tetestingin, gaano karaming pera/oras, at saan sa schedule.
  • Trade-off ang budget at schedule: kapag binawasan ang isa, mawawala ang coverage o speed.
  • Flexible pero risk-focused ang testing.
  • Good test administration = smart planning + realistic budgeting + risk-based schedule → documented at signed-off na final report.
